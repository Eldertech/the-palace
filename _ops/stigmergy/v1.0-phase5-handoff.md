## The standing discipline (do not relearn these the hard way)

1. **NEVER `git add -A`.** Stage only explicit paths. A concurrent session's uncommitted work was once swept into a STIGMERGY commit via `-A`. Every commit this session used an explicit path list. The `palace-commit.mjs` tool enforces this (it only stages `--path` args).
2. **Commit each phase the moment its gate is green.** Don't let working-tree edits sit while anything else might write. Several near-losses came from holding uncommitted work across interruptions.
3. **Clear stale locks before committing:** `rm -f .git/index.lock .git/HEAD.lock`. Cowork/concurrent sessions leave them; they abort `git add`.
4. **The actuator must never fire a real `claude` during build/test.** It is stub-gated: tests inject a `buildArgv` that runs `tests/fixtures/stub-worker.mjs` (which carries the `bypassPermissions` signature so the ps-liveness check still exercises). The dev server fires the stub only when `STIGMERGY_STUB_WORKER=1`; `GET /api/worker` reports `stubbed`. A fire-through e2e/capture HARD-GATES on `stubbed` so it refuses to run against a real-worker server.
5. **Gate, then validate, then commit -- in that order.** Once this session I committed a failing gate (a test asserted the wrong stage transition) and had to amend. Run `npm run check:phase-N`, confirm `GATE_EXIT=0`, dispatch the vision-validator subagent, THEN commit.
6. **The dev server:** `cd app && STIGMERGY_STUB_WORKER=1 npx vite --port 5173`. Playwright reuses it (`reuseExistingServer`). Node v25 cannot `node --check` a `.jsx` file (`ERR_UNKNOWN_FILE_EXTENSION`) -- that is NOT a syntax error; validate JSX via vitest/vite, or `node --check` only plain `.js`.
7. **Big tool batches get cancelled by harness hiccups mid-run and waste work.** Prefer smaller sequential tool groups, especially for Writes. Re-establish ground truth (git status, `ls`, grep counts) after any interruption before assuming a file landed.

## Phase 5 — STATE write: THE DESIGN (Loudon's explicit ask)

Loudon's instruction, verbatim intent: *start with dry-run, test for a bit, then shift to a streamlined write-enabled workflow. Design now how the streamlined one interacts with git best (worktrees, commit naming, etc.) so we're ready when we go full-edit. And scope STIGMERGY to avoid disasters.*

### Stage A — Dry-run by default (build this first, gate it, commit it)

The STATE editor (frontmatter forms + body editor) is built and fully wired to `palace-commit`, but the live save defaults to **preview/dry-run**: clicking Save shows the exact structured commit it WOULD make (subject + derived `Palace-*` trailers + the unified diff) without writing the file or committing. `palace-commit.mjs --dry-run` already produces this; the editor calls it. This is the safe default, mirroring the stub-gated actuator. Gate Phase 5 in this mode: a Playwright test edits a frontmatter field, clicks Save, and asserts the preview shows the correct `Palace-Stage`/`Palace-Vector` trailers -- against a TEMP palace, never the real one.

### Stage B — Armed writes (design now, build only when Loudon says go)

When Loudon arms writes (`STIGMERGY_ARM_WRITE=1`, parallel to `STIGMERGY_STUB_WORKER`), Save writes the `.md` and commits via `palace-commit`. The design, worked out so it's ready:

**Git interaction -- worktrees.** The disaster risk is STIGMERGY committing onto whatever branch is checked out while another session (or Loudon in Obsidian) is mid-edit. The fix Loudon flagged: **STIGMERGY edits in its own `git worktree`.**
- On first armed save, STIGMERGY ensures a dedicated worktree, e.g. `git worktree add ../palace-stigmergy-edits stigmergy-edits` (a long-lived branch `stigmergy-edits`). All STATE writes + `palace-commit`s happen THERE, never in Loudon's working copy.
- A periodic/manual "publish" merges `stigmergy-edits` into the main line under review (this IS the Phase 6 reconciliation / audition surface -- review-the-diff before merge, per [[Closing Well]]).
- Benefit: STIGMERGY can never clobber an in-flight Obsidian edit, because it is literally a different checkout. Concurrent writes become a merge (surfaced, reviewable), never a silent overwrite.
- Caveat to resolve at build time: the dev server reads palace files from `PALACE_ROOT` (main checkout) for STATE *read*; armed *writes* target the worktree. Either point writes at the worktree path explicitly, or run a second server instance rooted in the worktree. Recommend: `palace-commit` takes a `--worktree <path>` and writes there; STATE read stays on the main checkout so the reader sees the published truth, and a "pending STIGMERGY edits" banner (from the worktree's uncommitted/unmerged state) shows what's staged for publish. This dovetails with Phase 6.

**Commit naming.** Already solved by Phase 3. STATE-write commits use `palace-commit --kind edit --scope "<Entry>" --summary "<what>" --verify <call>`; trailers (`Palace-Entry`, `Palace-Stage`, `Palace-Vector`) are derived from the staged frontmatter diff automatically. Author is `claude` (or, when a human drives the form, consider `Palace-Author: loudon` -- decide based on who's at the keyboard; the form could ask). Multi-field edits in one save = one commit. Add `Palace-Campaign: stigmergy-state-edit-YYYY-MM-DD` if a session makes many.

**Scoping STIGMERGY to avoid disasters (the guardrails):**
- **Path allow-list.** Armed writes may only touch entry `.md` files and their bundle files inside the palace root -- never `.git/`, `.claude/`, `_ops/` machinery, `SCHEMA.md`/`CLAUDE.md`/other canon (canon edits stay show-before-write in the Claude conversation). Enforce in `palace-commit` AND in the write endpoint, not just the UI.
- **Frontmatter forms make schema-violation impossible** (the spec's §7 self-description test satisfied by the UI): `type` is a picker bound to the §1 enum; `stage` a stepper; `pillars` a multiselect; typed-link editor bound to the 10-type ontology with target-autocomplete against real entry titles (no dangling links). This is a feature AND a guardrail -- a form cannot emit an illegal entry.
- **No bulk/recursive writes.** One entry per save. No "apply to all." A runaway loop can't rewrite the palace.
- **The worktree is the blast radius.** Worst case, an armed mistake lives on `stigmergy-edits` and is caught at publish-review -- it never reaches main unreviewed.
- **Keep the audition gate hard-coded** (the Stage E lesson): never auto-publish sensory/irreversible work.

Write Stage B's design into `V1.0-PHASE-5-COMPLETE.md` when built, and surface the arm flag + worktree path to Loudon before first real write.
