# Baton: STIGMERGY v2.0 — posting half (generative tier next)

## Move
Open the next STIGMERGY v2.0 posting-half increment with Loudon. The **detection
tier is done** — both mechanical scan-based proposal types ship (`promote_unsung`,
`promote_hub`) with three executor ops (`set-vector`, `add-link`, `set-type`). The
next rung is the **generative tier**; recommended start is **`vector_tuning`**
(propose a sharper `forward_vector` for an entry, applied via the already-shipped
`set-vector` op — so the new work is the *generation/reasoning* side, not executor
plumbing). It is a genuine step up in *kind*: unlike a pure `findX` scan, it needs
an agent to read an entry against its body and judge — so it leans on the
orchestrator/worker, not a detector. The fork is Loudon's (see Next move).

## Why this move matters
The detection types were bounded because they're mechanical (a scan + a threshold).
`vector_tuning` is the first type that needs *taste*, which is why the roadmap files
it under "harder — needs real Weave reasoning." Naming it as the next move keeps the
posting half growing on the proven scan→plan→post→grant&apply spine while crossing
the line from detection into generation deliberately, not by accident.

## Tried and rejected (this session — don't re-explore)
- A third *mechanical* detection type after unsung+hub → there isn't a clean one;
  vector-tuning / mirror-sweeps need reasoning, not a threshold. That's the point of
  the tier boundary.
- Generalizing `POST /api/weave/emit-unsung` into one param'd route → kept parallel
  routes (`/emit-unsung`, `/emit-hub`) per how the codebase already grew; lower-risk.
- New QUEUE card code for `promote_hub` → not needed; a single-entry `vector_proposal`
  with null `target_entry` renders fine and "grant & apply" lights up once the op
  normalizes. A `vector_tuning` proposal should reuse the same path.

- The **shared owner tree carries other agents' in-flight work** — **stage explicit pathspecs, never `git add -A`**, and verify the staged set before every commit.
- **Canon mutation needs show-before-write on the exact diff, even on "run"/"demonstrate"** — the auto-mode classifier blocks a live canon edit without the precise change shown first. Show the diff → explicit confirm → run.
- Bash safety classifier can have a transient outage ("temporarily unavailable") — retry; read-only tools stay up.
- Commits: `ops(stigmergy): …` + `Palace-Kind: ops` / `Palace-Verify: verified` / `Palace-Author: claude`. Subjects >72 chars get a harmless soft hook note.
