## Smoke-test in 60 seconds

```bash
cd _ops/stigmergy/app
npm run dev
```

Open `http://localhost:5173/`. Type any handle, click `[L] JACK IN`. You
should land on the **GENERAL board** of the real palace persistent
blackboard. Tabs `[1]–[6]`. Hotkey `[V]` toggles scanlines (and the
status-bar `VFX: ON|OFF` indicator).

To see the full demo data (synthesized messages covering every type and
channel), open `http://localhost:5173/?demo=1`. Demo data is *prepended*;
the real palace data still loads underneath.

## What v0.1 is

A read-only browser terminal for the palace's BBS Blackboard. Reads
`_ops/swarm/persistent/blackboard.jsonl` (113 messages on disk today)
and `_ops/swarm/sessions/<id>/blackboard.jsonl` (zero session
sub-directories on disk today). Renders messages with the full
STIGMERGY visual language: phosphor green on terminal black, VT323
banners, IBM Plex Mono body, CP437 box-drawing, no rounded corners,
no emoji.

## What v0.1 is not

Not a way to post messages. Not a daemon. Not the orchestrator from
the Palace Agent Infrastructure Spec. Not a Trickster-action surface.
All of that is v0.2+.

To respond to a Trickster RESOURCE_REQUEST in v0.1: edit
`_ops/swarm/persistent/blackboard.jsonl` directly. The UI displays the
exact path in an amber caption.

## Findings flagged for review

### Findings — design system

The design-system at `_ops/stigmergy/design-system/` is the source of
truth for visual tokens. Per the production plan I did not modify it.
But during the build I discovered three real issues that need
addressing in a v0.2 design-system pass:

1. **`fonts/IBMPlexMono-Regular.woff2` and `IBMPlexMono-SemiBold.woff2`
   are corrupt HTML stubs, not woff2 files.** They are 1623 / 1624
   bytes and start with `<!DOCTYPE html>`. The valid font is
   `VT323-Regular.woff2` (6740 bytes, real wOF2 magic). I downloaded
   real woff2 files from `@fontsource/ibm-plex-mono@5.0.13` via
   jsDelivr into `app/public/fonts/` only — the broken originals are
   untouched.
2. **`assets/welcome_screen.txt` has "BLACKBOARD" in the big ASCII art.**
   The design system's own README §"The Name Rule" says the product
   name in all UI copy is **STIGMERGY**, and "BBS Blackboard" is
   internal-only. The asset violates this. I replaced it with an inline
   STIGMERGY banner in `LoginScreen.jsx`; the asset is untouched.
3. **`assets/welcome_screen.txt` uses em dashes (`——`).** The design
   system's content rules say "No em dashes (use `--`)." I'd already
   substituted them at render time before discovering issue #2 above
   pushed me to inline-replace the whole banner.

`colors_and_type.css` itself is otherwise solid and remains the source
of truth for tokens. `src/styles/tokens.css` mirrors it — see the
header comment in that file for why we mirror rather than `@import`
(the design-system's `@font-face` rules pull in URLs that 403/404,
which keeps `document.fonts.check` returning false even when our local
override loads). Keep them in lock-step.

### Findings — real palace data

4. **The persistent blackboard at `_ops/swarm/persistent/blackboard.jsonl`
   is mostly schema-drifted.** Of 113 lines:
   - ~3 are FLAG-shaped messages (TRICKSTER-ARTIFACT, SPINOZA-ARTIFACT,
     APO-ARTIFACT, etc.) that have `id`, `from`, `to`, `type`, `board`,
     `payload` — but lack `schema_version` and `session_id` (they use
     `session` instead), and `ts` is a bare date `"2026-04-01"` not
     ISO 8601 with timezone, and there's no `health` block.
   - ~110 are audit-result dumps from past swarm runs with shape
     `{session, batch, entry, ts, result}` — none of the eight
     required §2.2 fields are present.
   - The UI makes both classes of drift visible via red borders + a
     `warnings: ...` line. This is intentional per the plan.

5. **The sessions directory `_ops/swarm/sessions/` does not follow the
   `<id>/blackboard.jsonl` shape the spec expects.** It contains flat
   `.md` and `.json` files (e.g.
   `swarm-2026-04-07-001-synthesis.md`,
   `mechanical-audit-2026-04-27.json`). The middleware's
   `/api/sessions` glob returns an empty list, which surfaces as the
   `NO SESSIONS YET. PERSISTENT BOARD ONLY.` indicator in the UI.

### Findings — minor design polish

6. **The handle: input underline on the LoginScreen uses CSS dashed
   border-bottom**, not CP437 box-drawing characters. Caught by the
   Phase 1 visual-validator as a "watch" note (not a checklist
   failure). v0.2 polish item.

7. **The Box primitive (`primitives.jsx`) had CP437 corners (`┌─┐ └─┘`)
   but DASHED CSS borders for the verticals**, creating a visible joint
   mismatch. Fixed in this build for `tone='single'` only (now solid);
   `tone='double'` still uses `border-style: double` which works fine.
   Could propagate the same fix to the design-system reference Box.

## Decisions Claude Code made worth your review

1. **`tokens.css` mirrors the design-system instead of `@import`-ing it.**
   The design-system file embeds `@font-face` declarations with two
   broken `src` URLs each. Even with our working override `@font-face`
   in place, the broken declarations stayed in the FontFaceSet and made
   `document.fonts.check` return false. Mirroring the entire token file
   was the cleanest fix. The trade-off: now there are two copies of the
   tokens that need to stay in sync. The header comment in tokens.css
   documents this.

2. **Replaced corrupt design-system fonts with real ones (in `app/public/fonts/` only).**
   Did NOT modify `design-system/fonts/`. The corruption is logged
   above as finding #1.

3. **`?demo=1` URL parameter** prepends a small set of synthesized,
   spec-conformant BBS messages covering every documented `type` and
   every `board`, used by the Phase 3 / 4 / 5 / 6 captures so the
   visual-validator has rich data to evaluate. Real palace data still
   loads underneath when demo is on. **Default usage (no `?demo=1`)
   shows real palace state only.** I think this is the right separation
   — flag if you'd prefer a different toggle (e.g., a UI button rather
   than URL param).

4. **Type-on speed scales with banner length.** The design system says
   `--dur-type: 20ms` for the type-on animation. At 20ms/char, the
   ~1300-char welcome banner takes 25 seconds — too slow. I scaled to
   `~2ms/char` so the banner completes in ~2 seconds. The 20ms value
   is appropriate for short H1-style headers; long multi-line banners
   need a different scale. Worth deciding whether to update the design-
   system rule or document this scaling pattern.

5. **`VFX: ON | VFX: OFF` indicator in the status bar.** Added because
   the actual scanline overlay is by-design extremely subtle and the
   toggle is invisible in still screenshots. The text indicator makes
   the toggle state legible without changing the scanlines themselves.
   The validator could not detect the scanline difference visually
   without it. If you'd rather rely on the visual effect alone, remove
   the indicator from `Shell.jsx` and bump the scanline opacity (which
   would deviate from the design-system's "~4% opacity" rule).
