# STIGMERGY v1.0 — Phase 4.5 (Enrichment consolidation) — COMPLETE

Autonomous build per `_ops/stigmergy/v1.0-build-handoff.md` (Revision 2 §3). Gate green: **343 vitest + 10 e2e + 2 captures**, vision-validator pass. **Branch:** `stigmergy-v1.0-frontend-rebuild`. **Not pushed. The Flask server is superseded, not deleted** (see "What this does NOT do").

## What Phase 4.5 is

The Enrichment ceremony's card loop, absorbed into QUEUE. The card model, the validator-verdict strip, and the deposit/revise/discard response loop now live inside STIGMERGY's QUEUE deck, driven by the Phase 2.5 actuator. The board you read is now the board that *acts* on enrichment cards.

Scope, per Loudon's call: **render + stub-fire**. Cards render and the response loop is fully wired (writes the inbox block + fires the supervisor through the actuator), but the fire path is the same guarded, stub-gated primitive proven in Phase 2.5 — real `claude` only spawns when explicitly armed, never during the build/test path.

- **`src/lib/card-model.js`** (pure, 8 unit tests) — mirrors `Enrichment/server.py:load_cards`: `detectArtifactType`, `isArchived`, `normalizeCard` (target/purpose/fv/summary + validator fields + artifact URL), `sortCards`, `verdictTone`.
- **`server/cards.js`** — the Node re-implementation of the card I/O STIGMERGY now owns: `readCards` (reads `Enrichment/card-*` folders, skips archived, reads text artifacts inline) and `appendInboxBlock` (writes a response to `Enrichment/inbox.md`). The inbox header + block envelope **match `server.py` exactly** (`# Enrichment Inbox`, `## id — target`, `**received:** · **purpose:**`, the `---` rule) so the existing supervisor parses STIGMERGY-written blocks identically — with the structured `action:`/`note:` carried as the block text.
- **`src/components/queue/CardItem.jsx`** — one card as a QUEUE item: the `enrichment` tag, target, purpose, summary, the validator-verdict strip (verbose mode) with a `[+] validator note` toggle, the artifact rendered inline (text → `<pre>`; image/audio/iframe → `ArtifactSlot`, the existing rich-content engine), and deposit/revise/discard/more-like-this controls (revise opens a one-lever note field).
- **`QueuePanel`** gains an `ENRICHMENT CARDS` section below the ranked items; responding posts to `/api/cards/respond` and refreshes after the worker has a beat.

## Endpoints added

- `GET /api/cards` — the card queue (reads `Enrichment/card-*`, normalized + sorted).
- `POST /api/cards/respond` — body `{ cardId, action, note?, targetName?, purpose? }`. Writes the inbox block, then fires the supervisor (`Enrichment/supervisor-prompt.md`) through the actuator. A refused fire (worker already alive) is **not** an error — the inbox write succeeded and the live worker picks it up.

## Proven safely

- **Write + fire path** is proven hermetically by `tests/integration/cards-middleware.test.js` against a **temp palace** with a **stub-backed actuator** — it asserts the inbox block is written in the exact `server.py` envelope and the (stub) supervisor fires, including the "worker busy → inbox still written, not re-fired" case. No real palace file is touched; no real `claude` spawns.
- **The e2e (`card-queue.spec.js`) is render-only** against the live palace's real 6 cards — it verifies the section, the cards, the verdict strip, and the action controls render, but **never clicks** deposit/discard (which would write the real `inbox.md`). The captures are likewise read-only.

## What this does NOT do

- **The Flask server is not deleted.** `Enrichment/server.py` is superseded — STIGMERGY now owns the read + inbox-write + fire. Deleting it is a separate, deliberate cleanup (it still works standalone; removing it while it may be in muscle-memory use is the kind of move that deserves its own commit + Loudon's nod). The doc-rewrite the foundational-doc addendum §4 calls for (Enrichment Ceremony "Infrastructure" section) is queued with the other canon edits awaiting show-before-write.
- **The `card-validator` gate is not re-run from STIGMERGY.** STIGMERGY *renders* the verdict the supervisor already recorded on each card (verbose mode). Re-validation happens inside the fired supervisor run, where the `card-validator` subagent already lives — STIGMERGY does not duplicate it.
