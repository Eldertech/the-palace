## What Phase 19 is

The convergence of the two halves the BBS already had: the **Enrichment actuator**
("a board action fires a headless `claude -p` worker") and the **palace-orchestrator's
permanent-steward cycle** (`buildCyclePrompt` to assemble the cycle, `processCycle` to
validate → append → reconcile `pending_requests`). A new **STEWARDS deck** (hotkey `W`)
lets Loudon advance any steward — or all ready ones — by one cycle, consuming the
TRICKSTER grants made on the board, with no Claude Code session.

The keystone realization: a fired `claude -p ... --output-format stream-json` emits
exactly the transcript shape `processCycle` already parses. So the actuator's
fire→exit loop becomes the orchestrator for a steward cycle, reusing both modules
unchanged. The grants are already in the board slice `buildCyclePrompt` injects, so the
worker sees and acts on them with no special plumbing.

## How it works

1. `POST /api/steward/advance {name}` → the **steward lane** (`server/steward-lane.js`)
   resolves the agent via `REGISTRY.json`, captures `iteration`/`cycleN`/`tsNow` before
   firing, builds the cycle prompt, and fires a `claude -p` worker on a dedicated lane
   (`.actuator-steward/`), capturing stdout to a per-cycle transcript.
2. On the worker's exit, the lane's **reap** runs `processCycle` against that transcript
   (strict §2.2 validate → append valid messages → reconcile pending→resolved → write
   `state.json` + `history.jsonl`), stamped `dispatched_by: "bbs-actuator"`.
3. A small in-memory FIFO queue gives **batch advance**: the reap fires the next ready
   steward, so "advance all ready" drains serially (single worker per lane).

## Endpoints added

- `GET  /api/stewards` — every registered steward with `grants_waiting` (answered asks
  not yet consumed) + lane worker status / batch progress / last reap summary.
- `POST /api/steward/advance {name}` — advance one (404 unknown, 409 busy, 400 missing).
- `POST /api/stewards/advance-all {names?}` — advance every ready steward serially.

## Proven safely

- The full advance→consume is proven deterministically at the integration layer
  (`stewards-middleware.test.js`): a temp palace seeded with a request + matching grant;
  after advance the grant moves pending→resolved, the worker's message lands on the
  board, history records `bbs-actuator`. Batch drains two stewards serially.
- The `STIGMERGY_STUB_WORKER` gate covers the steward lane; when stubbed on the live
  dev server it fires the harmless stub AND sets `dryReap` so an e2e fire never mutates
  the real palace. Tests inject `opts.stewardLane` (a temp-palace lane). No build/test
  path spawns a real `claude`.
- The reap is wrapped so a `processCycle` throw can never escape the worker's exit
  handler (which would crash Vite); failures land in `.worker.log` + `last-cycle.json`.
- The actuator extension (`onExit` + per-cycle `transcriptPath`) is backward-compatible:
  all 7 existing actuator tests pass unchanged.
