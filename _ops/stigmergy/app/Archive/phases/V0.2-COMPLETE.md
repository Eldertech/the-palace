## New endpoints + features (v0.2)

- **`POST /api/persistent`** -- appends one §2.2-conformant message to the persistent blackboard; returns 400 + `{errors:[...]}` on validation failure; nothing written on rejection.
- **`POST /api/sessions/:id`** -- same contract scoped to a session board; creates the session directory if it does not exist.
- **`GET /api/persistent/stream`** -- SSE stream; emits new lines as `event: message` frames; supports `Last-Event-ID` for reconnection.
- **`GET /api/sessions/:id/stream`** -- same, scoped to a session; 404 if session file missing.
- **Click-to-respond flow** -- TRICKSTER inbox response options are real buttons; clicking opens `ResponseModal.jsx` with a full JSON preview; CONFIRM POSTs; CANCEL returns to inbox. The "EDIT the file to respond" caption is gone.
- **Live-tail status indicator** -- replaces the prior static `uplink ok` text; shows `● LIVE`, `● RECONNECTING`, or `● OFFLINE` reflecting the SSE connection state.
- **Optimistic inbox state** -- after a confirmed response the request disappears immediately from the inbox; SSE arrival deduplicates by `id` so the confirmed message is not double-counted.

## Decisions Loudon should review

1. **Missing-session-file behavior on SSE**: `GET /api/sessions/:id/stream` returns 404 if the session file does not exist, rather than watching the parent directory for file appearance. The 404 approach was chosen for simplicity. If the orchestrator creates sessions dynamically during a run and the UI is opened before the first write, it will need a manual reconnect after the file appears. Wait-and-watch is deferred to v0.3 if orchestrator-driven session creation becomes live.

2. **Custom-response option produces a RESOURCE_GRANT**: the "Custom response" inbox option creates a `RESOURCE_GRANT` with the typed text in `payload.constraints` rather than prompting for GRANT vs DENY. One-click-to-modal flow was the priority. If usage shows people often want DENY with a typed reason, the option shape needs revision.

3. **`re:` field correlation fix in Phase 4**: Phase 2's `response-builder.js` originally set `re: request.id` (the message `id` field). Phase 4 corrected this to `re: request.request_id ?? request.id` after discovering the inbox correlation uses the `request_id` payload field. The original Phase 2 unit tests passed because they set `id` on the fixture and asserted `re === id` -- they were testing the wrong correlation path. The fix is now correct against demo data and the inbox builder. Worth noting because the original passing tests were not catching the real bug.

4. **Pre-existing v0.1 e2e failures fixed in Phase 4**: `data.spec.js` and `health.spec.js` had tests that depended on the real palace board having specific schema-noncompliant entries -- the ones Loudon deleted on 2026-05-04. Phase 4 added two regression demo fixtures (`demo-flagged-1` and `demo-no-health`) and switched both tests to `?demo=1` so they exercise the lenient-render and missing-health-block paths against hermetic data going forward. If you run the suite without `?demo=1` those paths still render gracefully; the tests just needed stable data.

5. **Optimistic state lifted to App**: Phase 4 originally kept optimistic responses inside `TricksterInbox` local state. The visual-validator caught that the TRICKSTER tab badge count was stale after a confirmed response -- the badge derives from App-level state, not inbox-local state. Optimistic state was lifted to App so all derived state (counts, filters, inbox content, badges) sees the same set. Phase 5's SSE deduplicates by `id` when the same message arrives via the wire. The deduplication is by `id`; an optimistic-then-SSE arrival does not double-count.

6. **`live-reconnecting.png` capture skipped**: Phase 5 could not capture the reconnecting state because forcing it requires killing the dev server mid-test, which terminates the Playwright process. The `live-tail.spec.js` state-machine tests assert the RECONNECTING and OFFLINE paths structurally. If Loudon wants the visual sample: restart the dev server while the page is open and screenshot before it reconnects.

## Findings flagged for v0.3+

- **Orchestrator (Infrastructure Spec §3.2)** -- still a separate project. STIGMERGY v0.2 makes the board operational for humans; the orchestrator makes it operational for agents.
- **Always-on service / daemonization** -- `npm run dev` on demand still works; daemonize when the workflow demands it.
- **Persistent-board promotion ceremony (Infrastructure Spec §2.8)** -- coordinator-side, orthogonal.
- **Authentication / multi-user** -- single-operator continues.
- **Trickster broadcast UI for non-RESOURCE_REQUEST manual posts** -- file-edit fallback works; UI surface deferred.
- **Session-selector UX improvements** -- functional but minimal; richer browsing/filtering is v0.3.
- **Live-tail backpressure** -- not a concern at human-driven write rates; batch handling if the orchestrator floods the board.
- **`live-reconnecting.png` capture** -- see Decisions §6 above.
- **Schema validator drift risk**: the v0.1 read-side lenient validator (`src/lib/schema.js`) and the v0.2 write-side strict validator (`server/validator.js`) are now independent. Read-side stays lenient by design (diagnostic value of seeing malformed messages). If §2.2 evolves to a §2.3, both validators need updating. A note in v0.3 if a schema revision lands.
- **Wait-and-watch SSE for missing session files** -- see Decisions §1 above.
