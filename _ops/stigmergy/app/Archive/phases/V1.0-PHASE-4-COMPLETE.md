## What Phase 4 is

QUEUE reframed as the prospective deck: **one ranked inbox of everything open**, not six round-robined board tabs. A board that never claims past facts cannot lie about them (Two Batons / Drift and Consolidation), so QUEUE holds only open, future-facing items and closes them by git events.

- **`src/lib/queue-model.js`** (pure, 24 unit tests) — the heart:
  - `buildQueue(messages)` → unified items from unanswered `RESOURCE_REQUEST`s and `handoff_ready` BROADCASTs, ranked (blocking first, then newest). The item type set is open (proposals + audition gates later).
  - `reconcileQueue(items, commits)` → marks an item resolved when git satisfies its `stale_if`: a commit carries `Palace-Resolves: <item.id>`, OR a commit touched the item's entry **after** it was posted. Never mutates inputs; resolution is advisory.
  - `partitionQueue` / `laneCounts` / `rankQueue` / `vantage` helpers.
- **`src/components/queue/QueueItem.jsx`** — one honest item. Asserts an act at a time from a vantage (`announced HH:MM:SSZ, from X`), names its `stale_if`, points to live state (a STATE-entry chip). When git resolves it, it greys (struck-through summary, dimmed edge) with "looks done -- <reason>. clear it?" — the human confirms; nothing self-deletes silently.
- **`src/components/queue/QueuePanel.jsx`** — the unified panel. Builds from the live board feed, fetches `/api/log` for reconciliation, splits open vs looks-done, renders board-lane filter chips (boards as lanes, not tabs), and clears items locally on the human's confirm (the durable record stays git).

Wired into the QUEUE deck above the board view, beneath the Phase 2.5 actuator panel.

## The gate, proven

**"A handoff_ready appears and self-clears when a resolving commit lands."** Proven two ways:

1. **Deterministically at the unit level** — `reconcileQueue` resolves via `Palace-Resolves`, resolves via an entry-touch-after-post, does NOT resolve when the touching commit predates the item (honest staleness), matches entries case-insensitively, and never mutates inputs.
2. **End-to-end against real git** — the hermetic `?demo=only` feed carries two `handoff_ready` posts. One names entry **"Two Batons, One Board"** (which has real later commits in the palace history) → QUEUE fetches the live `/api/log`, reconciles, and renders it in the looks-done group with the resolving commit named. The other names a nonexistent entry → stays open. The e2e asserts the resolved item appears, shows "looks done", offers "clear it?", and that clicking it removes the card. Deterministic because the palace history for that entry is fixed.

## Honest-item discipline (the spec's core ask)

Every item names *what would retire it* and *when/from-where it was asserted* — never present truth. The resolved state is "looks done -- a commit touched X after this was posted", not "X is done". The human confirms the clear. This is the prospective (QUEUE) → retrospective (LOG) crossing made visible: an open intention becomes a closed fact only when git says so.

## Deferred (honestly noted)

- **Proposal + audition-gate item types.** The model's item set is open; Phase 4 ships the two proven types (resource_request, handoff_ready). Weave proposals land in Phase 5.5; audition gates ride Stage E's existing digest (rendered, not replaced).
- **Entry-targeted jump.** The STATE-entry pointer currently switches to the STATE deck; deep-linking to the specific entry is a small Phase 5/6 refinement (STATE deck would read a target).
- **`handoff_picked_up` actuator dispatch.** The model recognizes a `handoff_picked_up` ack (drops the item); firing a worker to *pick up* a handoff from QUEUE is Phase 4.5 (it rides the actuator).
