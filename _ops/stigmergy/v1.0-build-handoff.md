# Handoff: STIGMERGY v1.0 — Palace Front-End (build)

## Step 0 — Checkpoint the palace first (before any build)

Loudon wants a safe, returnable snapshot of the whole palace committed **and pushed** before this STIGMERGY v1.0 work goes further — so if the direction turns out wrong, there is an exact point to return to. Git from Cowork can't push (the remote is SSH and the credentials live on the Mac; the Cowork sandbox fails host-key verification), so **this is your first action, before reading anything else as work.**

Run from the palace root, on the current branch (`stigmergy-v0.3-rich-content`):

```bash
# 0a. clear any stale Cowork locks (harmless if none)
rm -f .git/HEAD.lock .git/index.lock

# 0b. snapshot the entire working tree (.gitignore already excludes
#     .DS_Store, logs, .venvs, .obsidian junk — verified from Cowork)
git add -A
git commit -m "checkpoint(palace): full state before STIGMERGY v1.0 front-end build

Captures the v1.0 design contract, build handoff, and foundational-doc
addendum plus all in-flight work, as a returnable point.

Palace-Kind: ops
Palace-Verify: verified"

# 0c. mark it as a named, returnable checkpoint
git tag -a checkpoint-2026-05-29-pre-stigmergy-v1 \
  -m "Palace state before STIGMERGY v1.0 front-end build. Return here if the front-end direction is abandoned."

# 0d. push the branch (set upstream) and the tag to GitHub
git push -u origin stigmergy-v0.3-rich-content
git push origin checkpoint-2026-05-29-pre-stigmergy-v1
```

**To return to this checkpoint later** (if the build proves a bad direction): `git checkout checkpoint-2026-05-29-pre-stigmergy-v1` to inspect it, or `git reset --hard checkpoint-2026-05-29-pre-stigmergy-v1` on a branch to roll fully back. The tag is immutable and independent of any branch, so it survives whatever the build does.

Only **after** the checkpoint commit and tag are pushed do you create the `stigmergy-v1.0-palace-frontend` build branch and begin Phase 1. Report the pushed commit SHA and the tag name back to Loudon before building.

## Move

Build STIGMERGY v1.0 — the palace's three-deck front-end (**STATE** / **QUEUE** / **LOG** = present / future / past) — per the design contract, by extending the existing v0.4 app, and in doing so **absorb the Enrichment server's `_fire_worker` actuator and card-review loop** so QUEUE can actually dispatch work, not just display it.

## Why this move matters

The palace is worked from two BBS-style surfaces today (STIGMERGY at `:5173` read-only-ish, the Enrichment Flask server at `:7878` which can actually fire Claude workers) and from Obsidian (which holds truth but renders it badly). v1.0 collapses that into one terminal whose top-level navigation *is* the retrospective/prospective discipline, and whose QUEUE inherits the one mechanism the board always lacked: an actuator. The keystone realization of this session — `_fire_worker` is the "board → fired `claude -p` worker" primitive that [[Two Batons, One Board]] said the board didn't have. Absorbing Enrichment is therefore not cleanup; it is how the board stops being a pheromone field and becomes an actuator.

## Enrichment server — the process and lessons to carry

This is the part most worth getting right. The Enrichment ceremony already proved the interaction model and the actuator; inherit both.

**The loop that works:** the server renders a rolling queue of ~5 cards; the human responds by writing a block to `inbox.md` (deposit / revise / discard / tweak-vector / graffiti); on submit the server **fires a single headless worker**; the worker reads the inbox, acts (deposits an artifact into the target entry's *bundle root* with a descriptive name and edits the body inline; or revises; or discards), then tops the queue back to 5; a `card-validator` subagent in fresh context gates every fresh or regenerated card (pass / revise[cap 1] / kill). In QUEUE terms: cards become QUEUE items, the inbox becomes QUEUE actions, the worker-fire becomes dispatch, the validator becomes a QUEUE-side gate.

**The actuator (`_fire_worker`) and its scars — port these exactly, in spirit:**

- Spawn `claude -p <prompt> --permission-mode bypassPermissions`, stdout/stderr → `.worker.log`, pid → `.worker.pid`. The `bypassPermissions` flag is load-bearing: `claude -p` has **no TTY** to answer Write/Edit permission prompts, so without it the worker hangs.
- **Existence ≠ liveness.** Before trusting a pid, verify it is actually a `claude` process (`ps -p <pid> -o command=`) — the OS reuses pids, and a recycled pid will falsely read as "worker alive." This is `_pid_is_our_worker`. Do not skip it.
- **Daemon-thread cleanup.** When the worker exits, remove `.worker.pid` — otherwise stale pid state blocks the next fire. Without this the surface wedges silently.
- **Single global worker** per queue; refuse a second fire while one is alive.

**Backend decision (resolve it, then note it in `V1.0-PHASE-2.5-COMPLETE.md`):** STIGMERGY is Node/Vite; `server.py` is Python/Flask. Recommended: re-implement `_fire_worker` with Node `child_process.spawn` and retire the Flask app; fallback is keeping a thin Python sidecar STIGMERGY calls. **Carry the lessons, not the language** — the liveness check and daemon cleanup are the parts that took real debugging, and they must survive the port whichever way you go.

## What NOT to do

- **Do not run the Weave, Map Build, or Self-Model inside STIGMERGY.** They stay Claude-side swarm/solo ceremonies. STIGMERGY renders their *output* (Topology Lens), inboxes their *proposals* (QUEUE), records their *edits* (LOG). It is not a ceremony engine.
- **Do not make STATE the primary authoring surface.** Eight of eleven ceremonies author in the Claude conversation under show-before-write. STATE editing is a secondary path for quick tweaks + the structured-frontmatter guarantee.
- **Do not hard-block out-of-band commits.** The `commit-msg` hook tolerates-and-annotates (`ops`/`couldnt`); it must never wedge Loudon's Obsidian or CLI commit.
- **Do not violate the locked aesthetic.** No login screen; CSS borders evoking CP437, not character-cell ASCII rules; no page-width cap (only ~78ch on message body); no cyan-as-primary, no emoji, no em dashes (use `--`). When in doubt, read the design-system SKILL.
- **Do not assume a single writer.** The repo is mutated concurrently by multiple Claude sessions, the steward batch, and the (soon-absorbed) enrichment worker. Never silent-overwrite.
- **Do not let QUEUE auto-resolve anything sensory or irreversible.** The audition gate is hard-coded (the Stage E lesson). QUEUE *renders* Stage E's digest; it does not replace its ruleset engine.
- **Do not lose the Enrichment robustness scars** when porting the actuator (see above).
- **Do not push the branch** until Loudon smoke-tests.

## Calibrations from this session

- Loudon does ~100% of commits today; `palace-commit` should be the single producer of structured commits, the hook the tolerant backstop.
- The STATE/QUEUE/LOG = present/future/past spine is non-negotiable — it is the literal top-level nav and the whole answer to "make the retro/prospective split frictionless."
- QUEUE items are honest: they assert an act-at-a-time, name `stale_if`, and point to live state — they never declare present state as fact.
- "Carry the lessons, not the language" on the Flask→Node port.

## Completion / stop conditions

Complete when all phases have a `V1.0-PHASE-N-COMPLETE.md` and the end-to-end reconciliation gate passes, on an unpushed `stigmergy-v1.0-palace-frontend` branch awaiting Loudon's smoke-test. A stop is a finding to report, not a failure to hide ([[Closing Well]]).
