EQUATION RENDERING

STIGMERGY · phosphor-native math · four proposals + recommendation

The problem in one line: free-text message bodies go straight through <Linkify> with white-space: pre-wrap, so any LaTeX ($$…$$, $a_k$) prints as raw source. Meanwhile a structured EquationBlock.jsx already exists and already encodes the house rule in its own comment: no KaTeX / MathJax / CDN — terminal-native monospace, dual-channel symbolic + worded. So the design question isn't "how do we render math" — it's "how do we honor that rule while making prose math just work."

0 · TODAY the bug
The core equation is almost embarrassingly simple. Each sample is a weighted sum of past samples, plus a leftover: $$x[n] = \sum_{k=1}^{p} a_k \, x[n-k] + e[n].$$ The coefficients $a_k$ are the prediction; $e[n]$ is the residual.
What ships now. Raw TeX, no layout. Authentically ugly — and the \, and {} noise actively hurts readability.
A · KaTeX, SKINNED off-grid

The coefficients are the prediction; the leftover is the residual:

Real math engine, recolored green + glow. Fractions stack, Σ is a true summation. But KaTeX ships its own proportional math-italic / serif fonts — you can recolor them, you can't grid them. It reads like a textbook wearing a CRT costume. Also: violates the no-KaTeX / no-CDN house rule and adds ~280 KB. Shown only so the tradeoff is concrete.
B · MONOSPACE GRID terminal-native

A small LaTeX-subset renderer lays the equation out on the character grid — Unicode sub/superscripts, a true stacked Σ, fraction bars drawn as CSS rules:

x[n] = pΣk=1 ak · x[n−k]  +  e[n]

Fractions stack the same way — here the all-pole transfer function:

H(z) = 11 − pΣk=1 ak z−k
Glows correctly, sits on the grid, no dependency. Cost: someone writes the LaTeX-subset → layout parser (\sum, \frac, ^, _, \cdot, \,). Covers ~90% of DSP math; rare exotic constructs degrade.
C · DUAL-CHANNEL BLOCK house rule

Extend the existing EquationBlock convention: every display equation renders twice — symbolic, then worded with named variables — both on the grid. This is already the palace's stated math format.

Autoregressive model
x[n] = pΣk=1 ak · x[n−k]  +  e[n]
ak = prediction coefficients  ·  p = model order  ·  e[n] = residual
sample[n] = sum over k=1..order of ( coeffk · sample[n−k] ) + residual[n]
Most legible, most palace-native, zero new aesthetic risk. The worded line is authored at writing time (a writing standard going forward; past equations corrected by a weave task), never generated at render time. Doesn't auto-fix loose prose $…$ — it's for deliberate, framed display equations.
INLINE · everywhere ships first

Inline math needs no engine and should land regardless of which display option wins. A tiny pass turns $a_k$, $x[n-k]$, $z^{-k}$ into Unicode-prettified spans inside flowing prose:

In words: today is yesterday (and the day before, weighted) plus noise. The coefficients ak are the prediction; the term e[n] — the residual — is what prediction failed to catch. The transfer function H(z) = 1 / (1 − Σ ak z−k) has only poles, which is why an all-pole model can ring.

No fonts fight, nothing leaves the grid. Subscript/superscript via Unicode where it exists (₀–₉, ₖ ₙ ₚ; ⁻ ᵏ ⁿ), CSS <sub>/<sup> fallback otherwise. $…$ → chip, $$…$$ → one of the display blocks above.

Recommendation — C as the format, B as the engine, inline first

Ship the inline pass immediately: it's small, safe, and kills 80% of the ugliness in the screenshot with zero aesthetic risk. For display equations, adopt C (dual-channel framed block) as the format — it's already the documented house convention and it's the most legible — and build B (the LaTeX-subset grid renderer) as the engine that draws the symbolic line, so authors write normal TeX and STIGMERGY lays it out on the grid. The worded line is an author-time writing standard, not a render-time step — going forward equations are written with it; existing equations get corrected by a weave task. Reserve raw-TeX-in-a-labeled-panel as the graceful fallback for anything the subset parser can't handle. Reject A: KaTeX can't be gridded, and it breaks both the no-CDN rule and the phosphor look the whole front-end is built around.
