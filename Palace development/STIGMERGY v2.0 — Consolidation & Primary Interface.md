# STIGMERGY v2.0 — Consolidation & Primary Interface

> *Assessment, shipped consolidation, and roadmap. Written in the [[BBS Production Plan]] idiom. The locked aesthetic is [[BBS Design System]] — phosphor on black, VT323 + IBM Plex Mono, monospace structural. This document changes the architecture the aesthetic dresses, and corrects where the aesthetic had quietly drifted off-system.*

## Thesis

[[STIGMERGY v1.0 — Palace Front-End]] set the right spine: organize the whole interface by **time** — STATE (present / working tree), QUEUE (future / board), LOG (past / git) — so the honesty discipline (*nothing is real until it lands in LOG*) becomes the shape of the screen, not a rule to remember. That spine is sound and stays.

But the v1.0 thesis was never fully landed, and was then partly reversed. v1.0 said: three decks; the six boards (`GENERAL/FLAGS/WEAVE/SYSTEM/TRICKSTER/BRANCHES`) **demote** to lanes inside QUEUE. The build instead grew to **five** decks (TRICKSTER + STEWARDS were re-promoted, 2026-06-05) and the QUEUE deck **stacked the new ranked inbox on top of the old v0.x board-viewer** rather than replacing it. Two navigation paradigms, layered. v2.0 is the work of finishing the migration and then driving STIGMERGY from *a front-end Loudon watches* to *the primary surface Loudon operates*.

## The assessment (2026-06-16)

**Sound:** the time-deck spine; the wire (SCHEMA §9, hardened v1.10→v1.12; `@stigmergy/core`; strict validator; SSE); stewardship (19 permanent stewards on bundle-local plans); the Companion (Tier-A in-place edits). The mechanics are ready for the next stage.

**The drift that made QUEUE confusing** — two paradigms stacked produced three concrete defects, all now fixed in Phase 0:
1. **The same decisions rendered in three places** — the TRICKSTER deck (`TricksterCard`), the QUEUE ranked inbox (`QueueItem`, a "trickster" lane), and an in-QUEUE `TricksterInbox`+`DigestPanel` block — two of them co-rendering inside QUEUE. This *was* "the queue duplicates the trickster tab."
2. **Two board selectors on one screen** — `QueuePanel`'s lane chips and a second `ChannelTabs` axis, controlling two different views. This *was* "confusing and hard to navigate."
3. **The Trickster aesthetic drift** — `TricksterCard` reached for Loudon Live fonts (Cormorant serif headline, Manrope sans fold) inside a terminal that [[BBS Design System]] governs as monospace-only. The fold summaries actually rendered sans-serif; the headline carried a dead serif fallback (monospace only because `--font-body` happened to be defined). Root cause: v1.0's own line calling for the forward vector "in Cormorant-register prominence" — a phrase that contradicted the governing system.

**Integration scorecard:** Stewardship ✅ · Companion ✅ · Weave ◑ (flags land; Topology Lens unbuilt) · Handoffs ◑ (`handoff_ready` spec'd; no scheduler) · Enrichment ⚠ (parallel Flask server still live) · Lens ○ (designed, unbuilt) · Enchantment ○ (practiced via stewards, not a callable ceremony).

**The honest gap:** STIGMERGY succeeds at stewardship visibility + decision triage. The *single surface for all palace operations* is partial — authoring still lives mostly in the Claude conversation + Obsidian; Enrichment runs its own server; Lens/Topology are unbuilt. The path: heal the surface first (Phase 0), then close the integration seams (Phases 1–3).

## The clean deck identities (after Phase 0)

| Deck | Time | Job |
|---|---|---|
| **STATE** | present | read + edit entries |
| **QUEUE** | future | *the open-work board* — proposals, flags, to-dos, ready handoffs; the raw per-board feed demoted to a collapsible firehose. **No decision cards.** Its unique value is the QUEUE↔LOG reconciliation engine. |
| **LOG** | past | git explorer |
| **TRICKSTER** | decide | *the one decision inbox* — `RESOURCE_REQUEST`s + the auto-Trickster escalation digest |
| **STEWARDS** | advance | the orchestrator roster control |

The crisp line: **TRICKSTER = a steward is waiting on your answer; QUEUE = everything else open you might act on, nothing blocked on you.**

## Phase 0 — Consolidation (shipped 2026-06-16)

- **Decisions live only on TRICKSTER.** `QueuePanel` now filters out `resource_request` items (`buildQueue` still models them — the model stays complete and unit-tested — the QUEUE *view* simply doesn't surface them). The duplicate in-QUEUE `DigestPanel`+`TricksterInbox` block was removed.
- **`DigestPanel` relocated to the TRICKSTER deck**, where the escalation digest + alignment-review verdicts belong — **below the decision cards and collapsed by default** (it's the auto-trickster *tuning* panel, not the decision list, so the cards lead), with its wire labels humanized per [[Speak Like a Person, Log Like a Protocol]] (e.g. `BLOCKING AUDITION` → "paused — needs your ear"; `audition_verification` → "listen + approve"; `auto-grant` → "would approve"). *(Refined 2026-06-16 after the digest first led the deck and leaked protocol jargon — Loudon flagged the confusion.)*
- **One board selector.** The `ChannelTabs`/`MessageList`/`AgentRoster` board-viewer is demoted to a collapsible "raw board feed" firehose **under** the ranked QUEUE — folded by default for focus, auto-open in demo/e2e.
- **One decision card.** `TricksterCard` is canonical; the redundant `TricksterInbox.jsx` was deleted; the duplicated `Linkify` was hoisted to `src/lib/linkify.jsx` (the long-deferred "Phase 6 convergence").
- **Pure monospace restored.** Cormorant/Manrope/`--font-ui` leaks in `TricksterCard` + `EntryBody` replaced with `--font-mono`/`--font-display`; zero Loudon Live fonts remain in the rendered DOM.
- **Verified:** `npm run build` clean · 1223 vitest green · live-DOM assertions on both decks (no duplicate inbox, zero decision cards in QUEUE, DigestPanel on TRICKSTER, no serif/sans) · affected board-viewer e2e (`tabs`, `command-bar-active`, `rich-content-roundtrip`) green. Retired `inbox.spec`/`click-to-respond.spec` (tested the removed in-QUEUE surface); redirected `digest-verdicts.spec` to the TRICKSTER deck.

## The roadmap (priority order, set with Loudon)

**Phase 1 — Coordination & autonomy.** Pull every creative loop inside the terminal.

- **Enrichment consolidation — done (2026-06-16).** The hard part was already shipped in STIGMERGY's Phase 4.5: the actuator (`_fire_worker` robustness — PID-liveness via `ps`, daemon cleanup, idempotent fire), the card I/O, and the card queue were ported to the Node server (`server/actuator.js`, `server/cards.js`, `POST /api/cards/respond`), all tested. This phase pointed every doc — [[Enrichment]], the supervisor prompt, [[Oblique Enrichment]], the app README — at STIGMERGY's QUEUE and **retired the Flask `localhost:7878` server** (`Enrichment/server.py` deleted; git-recoverable; nothing automated started it). *Correction to the earlier plan: enrichment cards stay in **QUEUE**, not TRICKSTER — they are open-work studio-visits, not blocked-steward decisions, so they belong on the open-work board.*
- **Launch Interactive v1 — done (2026-06-16).** A `handoff_ready` item in the QUEUE now exposes a **launch interactive** action: it hands the baton to a session you can *watch and steer* — a ready catch-the-baton prompt (`buildLaunchPrompt`) to paste into a fresh Claude Code / Cowork / Companion session — and posts the paired `handoff_picked_up` (`buildHandoffPickup`) so the item self-clears, while the baton's own On-pickup checklist still governs the real catch + file deletion. **The design choice (Loudon's): complex work wants a watchable, steerable interactive session, *not* a fire-and-forget headless catcher** (which suits enrichment but not a multi-step baton). The same "launch interactive" primitive is wanted next on enrichment cards, stewards, and steward-*requested* sessions — `buildLaunchPrompt` is `kind`-discriminated for exactly that. The autonomous scheduler (auto-fire without a human click) is deferred.
- **Launch Interactive — now on enrichment cards too (2026-06-16).** Each enrichment card in the QUEUE has a **launch interactive** action that opens a session to *work the card in dialogue* (sharpen the artifact, then deposit/revise/discard) — no pickup semantics, unlike a baton. The primitive generalized cleanly: `LaunchModal` is now **context-driven** (only handoffs get MARK PICKED UP) and `buildLaunchPrompt` carries a `card` kind beside `handoff`. Proven: a live card opens the card prompt with copy + no mark-picked-up; a handoff still shows mark-picked-up.
- **The Agent Construction Launcher — done (2026-06-17).** The deferred "Launch Interactive → stewards + steward-requested sessions" item, taken further than spec'd. Two moves. **(1) One-click into a real terminal.** A launched session no longer pastes a hand-rolled prose nudge — `POST /api/launch` → `server/launch.js` → osascript opens Terminal.app running `claude --model claude-opus-4-8 --effort high "$(cat …)"` (the prompt goes through a temp file to dodge all shell/AppleScript escaping; the model is the *exact id* because the `opus` alias resolves to 4.7-low-effort on Claude Code v2.1.x). The desktop app has **no** URL-scheme deep-link and `node-pty` embedding is **unsupported** (TTY + keychain), both verified — a real terminal is the supported path. **(2) Constitute the steward as a page-agent.** `POST /api/launch/agent` runs the orchestrator's `buildCyclePrompt` in a new **`mode: 'interactive'`** — the home page injected as identity + state + neighborhood-filtered board + the steward posture, *the same context the headless cycle gets* (one source of truth, per [[Pages as Agents]]); only the closing swaps to **narrate-every-write** (Loudon: tell me before any board post / file edit / commit). The construct-agent panel (`AgentLaunchModal`) makes the build **legible by JEWEL tier** (T0–2 the `@import` floor · T3 the injected identity) and **tunable**: Core knobs (model · effort · editable mandate) + context-layer toggles (identity + state locked; board · history · page-change · staging trimmable, defaults on) + a full constructed-prompt view. Reached from the **STEWARDS** roster *and* a **TRICKSTER** card's *open interactive* (a registered steward routes to construction with the decision pre-filled as the mandate; a non-steward asker falls back to the simple launch — no regression). Shipped across ~8 commits; full app + orchestrator suites green; verified in-browser end-to-end (the only step left unproven is the macOS automation grant on the first real LAUNCH TERMINAL).
- **Steward-requested sessions — done (2026-06-18).** The launcher already *reads + wakes* a steward; this closes the asking loop in both directions, so a steward can now *itself* call for a live session at a critical moment. **(1) The read/surface half.** A steward that posts a `RESOURCE_REQUEST` carrying `payload.kind:"interactive_session"` is no longer parking a yes/no decision — it is asking to be *launched* into a live session. Its TRICKSTER card now recognizes that kind (`buildInbox` surfaces `payload.kind`) and foregrounds a primary **"launch interactive session"** CTA + a **"wants a live session"** badge, suppressing the small corner action (one launch control, not two); the request's options stay as the decline/defer surface. The CTA routes through the deck's existing `onLaunch` — a *registered* steward opens the construct-agent panel with the request pre-filled as a session-aware mandate ("you asked for this session and he said yes; pick up where your request left off"); a non-steward asker falls back to the simple launch (no regression). An ordinary decision card is untouched. **(2) The emit half** — a new `steward.md` subsection (*Ask for a live session only when the work wants a conversation*) + a fourth decision-surface in `shared.md`, teaching *when* to self-request: a **rare** move, reserved for genuinely iterative, taste-driven *together-in-the-room* work (a single yes/no is an ordinary request; a pick between renders is a `choice`); it never escapes making (ship the current state first, the session takes it *further*); `blocking: false` (an offer to go deeper, not a gate); `options[]` are decline/defer paths, not a yes. Reused the type — **no Schema Ceremony** (`kind` rides in the opaque payload, like `enrichment_card` / `choice`); the message stays a `RESOURCE_REQUEST`. Verified: a Crystal Synthesizer session-request demo card; +6 unit + 3 e2e + the interactive-prompt smoke render green; full app (1264) + orchestrator (227) suites green; in-browser screenshots of the card + the construct panel.
- **Weave proposals — the apply-on-grant half landed (2026-06-18).** The QUEUE displayed + granted `vector_proposal`/`weave_flag`, but a grant was a *dead-end* — nothing made the proposed change; the edit still had to be made by hand in Obsidian. This wires the back half. A proposal may now carry a structured `payload.apply` op (validated by a shared `weave-apply-op.js` — one source of truth for client + server), and its QUEUE card gains a bright **"grant & apply"** action beside the plain grant (the Trickster deck's FILE / FILE & RUN pattern). Granting it posts the grant **and** runs the executor (`POST /api/weave/apply` → `server/weave-apply.js`): it edits the entry through the Companion's enforced honest-write path (`armedWriteEntry`, now `kind`-parameterized so it commits as kind `weave`) and posts a `weave_applied` PROOF to the WEAVE board carrying the commit hash. `trickster: true` lets it write canon — the operator's grant IS the consent (same rationale as the Trickster commit); branded `Palace-Author: weave`; undo is a `git revert` away. **Two ops shipped: `set-vector` (vector tuning, Increment 1) + `add-link` (promote-unsung / new-typed-link, Increment 2).** The latter adds `addLinkToFrontmatter` — the link counterpart to `setForwardVector`: churn-free insertion into the YAML `links:` block (append to a present block · `[]` → block form · absent → new block), matching existing indentation, with a parse-free duplicate guard and a §4-`LINK_TYPES`-validated type (never invent a link type, no self-link). No Schema Ceremony — the op rides in the opaque payload. Verified: unit (incl. 11 churn-free `addLinkToFrontmatter` cases) + integration (real temp repo: forward_vector rewritten / typed link appended, commit kind `weave`, valid `weave_applied` PROOF with `vector_change`/`link_change`) + route + e2e + screenshots; full app (1302) + orchestrator (227) green.
- **Weave proposals — the posting half begins: the unsung-path emitter (2026-06-18).** The apply side sat waiting for real proposals; this is the first thing that *posts* them. A CLI — `_ops/stigmergy/app/scripts/weave-emit-unsung.mjs` — runs the Weave's **unsung-path audit** (the named ceremony postcondition): it reuses the existing detection (`unsung-paths.js` `findUnsungEdges` + the entry scan) to find body `[[wikilinks]]` to known entries that aren't yet typed links, and emits `promote_unsung` `vector_proposal`s **carrying an `add-link` apply op** (type `connects-to`, the §4 default) — so each one lands in the QUEUE with a **grant & apply** that formalizes the link, churn-free. The whole loop, automated for the emblematic case: detect → propose → grant & apply → committed typed link. **Safe by construction:** DRY-RUN by default (`--post` to append), `--limit` capped with every drop logged (no silent caps), idempotent (skips pairs already carried by an **open or denied** proposal — a deny is a durable no), and writes only through the sanctioned validate-then-`appendMessage` path. The pure builder/planner (`src/lib/weave-propose.js`) is the testable core. Verified: builder/planner unit (9) + CLI integration (real temp palace + board: one proposal for the genuine unsung path, idempotent re-run) + a **real-palace dry run** (532 entries → 913 unsung edges, capped to 6, 903 logged as dropped); full app (1314) + orchestrator (227) green.
- **Weave proposals — the emitter, surfaced in the terminal (2026-06-18).** The CLI-only bounce is ended: the unsung-path audit now runs from STIGMERGY itself. A `POST /api/weave/emit-unsung` route (paralleling `api/weave.js`'s apply route) reuses the SAME pure pipeline as the CLI — the entry scan + `findUnsungEdges` + `planUnsungEmission` — behind a shared `server/weave-emit.js` `runUnsungEmission`; the QUEUE header gains a **"run unsung-path audit"** trigger. **Two-click, write-needs-intent:** the first click is always a **DRY RUN** (read-only) that surfaces honest counts — entries scanned · unsung · already-proposed · eligible · would-post · over-limit — and only if any are eligible does a separate **"post N proposals"** confirm seed them onto the WEAVE board (arriving via SSE, each with its own grant & apply). DRY-RUN is the route default too (a write happens only on an explicit `dryRun:false`); the same idempotent dedup + no-silent-caps discipline as the CLI. Verified: module integration (5: dry-run writes nothing · `dryRun:false` posts one valid `promote_unsung` · idempotent re-run · honest over-limit cap) + route wiring (4: default-dry-run · pass-through · status-mapping · malformed-JSON) + a Playwright spec (clicks the dry run, asserts the counts, never posts) + a **live dry run** against the real palace (532 entries → 913 unsung, 909 eligible, 6 planned, 903 logged dropped); full app (1323) + orchestrator (227) green.
- **Weave proposals — a second detection-based type: the hub-promotion audit (2026-06-19).** The posting half grows from one detector to two, on the proven `runUnsungEmission` shape. A `POST /api/weave/emit-hub` route + a **"run hub-promotion audit"** QUEUE trigger (beside the unsung one) over a shared `runHubEmission`: it detects **concept entries whose INBOUND typed-link degree has reached the SCHEMA §1 hub threshold (≥5)** (`findHubCandidates` — inbound degree per §4's "the Map computes the hub's inbound degree", concept-only since §1's promotion path is concept→hub), and emits `promote_hub` `vector_proposal`s carrying a **new `set-type` executor op** (`armed-write.js` `setEntryType` — the churn-free type-line counterpart to `setForwardVector`/`addLinkToFrontmatter`; validated against the §1 `ENTRY_TYPES` enum; the PROOF carries `type_change`). Same two-click write-needs-intent, DRY-RUN default, idempotent dedup, and no-silent-caps discipline. The QUEUE renders it with no new card code (single-entry `vector_proposal`, null `target_entry`; "grant & apply" lights up because `set-type` normalizes). Verified: unit (detection 5 + builder/planner 5) + integration (set-type apply on a real temp repo: concept→hub on disk, commit kind `weave`, PROOF `type_change`, 422 no-op/bad-type; runHubEmission 4) + route wiring (4) + Playwright (dry run, never posts) + a **live dry run** (533 entries → 50 concept candidates, top: The Shop 49 · Pages as Agents 39 · Quality Manifesto 37 · Hyperdimensional Prism 33); full app (1344) + orchestrator (227) green.
- **Weave proposals — the first GENERATIVE type: vector-tuning (2026-06-21).** The posting half crosses from detection into generation. Where unsung-path + hub-promotion emit from a pure scan, `vector_tuning` needs *taste*: a synchronous headless `claude -p` worker (`server/weave-generate.js`, Path 2, no API key — the same worker mechanism the actuator/companion/steward lanes use, in request/response form) reads ONE entry against its body and proposes a sharper `forward_vector` per the "conatus, not stasis" rule (SCHEMA §3, [[Entry Conatus]]) — emitted as a `vector_tuning` `vector_proposal` carrying the **already-shipped `set-vector`** apply op, so it lands in the QUEUE with "grant & apply" and **zero new executor plumbing** (the baton's whole point: the new work is generation/reasoning, not plumbing). CLI-first, as the unsung emitter was before its route: `scripts/weave-emit-vector-tuning.mjs` with `--entry "<title>"` (targeted) or `--scan` (a pure pre-filter — `findVectorTuningCandidates`, flagging missing / stasis-verb / thin vectors, skipping the meta + foundational skeleton). Same safety spine: DRY-RUN default — but it *generates* in dry-run, because for a generative type the proposed before→after IS the thing to review — writing nothing; `--limit`-capped (default 3, since each is a generation) with every drop logged; idempotent dedup against open/denied proposals; writes only via the validated `appendMessage` path. The generation seam is injectable (`runImpl` + a `WEAVE_VT_GENERATE_STUB` env hook) so tests never spawn a real model. Verified: unit (candidates 10 + propose/select 7 + generate 12) + CLI integration (4, stubbed generation: dry / post / idempotent / targeted); full app (**1384**) + orchestrator (227) green; a **live dry run** against the real palace (533 entries → 222 candidates, top-1 generated a real on-discipline vector carrying teaching + ancestry + obsolescence-awareness + an open question, nothing posted). *Two deliberate follow-ups: (1) surfacing in the terminal (an emit route + QUEUE trigger) is its own harder increment — a generation's multi-second latency doesn't fit the detection types' fast two-click dry-run; (2) the `--scan` pool currently includes non-knowledge `_ops/` files that merely carry frontmatter — tighten the candidate filter (or lean on `--entry` + per-proposal review) when scan-mode graduates to the terminal.*
- **Weave proposals — vector-tuning, now in the terminal (2026-06-22).** The two follow-ups the prior bullet named are closed. **(1) Surfaced as a QUEUE trigger:** a `POST /api/weave/emit-vector-tuning` route over a shared `runVectorTuningEmission` + a **"run vector-tuning audit"** trigger beside unsung/hub. The generative tier forced one deliberate re-cut of the two-click pattern — the detection audits build their proposals in the dry run, but a `vector_tuning` proposal needs an LLM call to exist, so the **dry run is a cheap SCAN ONLY** (candidate entries + honest counts, no model call, no write) and the explicit second click, **"generate & post"**, is where generation happens (each candidate is one `claude -p`, so the cap is low and the click reads clearly as a write). Posted proposals arrive via SSE into the WEAVE lane with the shipped "grant & apply". **(2) The `--scan` pool is tightened:** `findVectorTuningCandidates` now requires a recognized SCHEMA §1 entry `type`, so the non-knowledge `_ops/` frontmatter (`type: agent-prompt`, bundle files, batons) that bloated the count is excluded — only real entries are tuned. Verified: full app (**1395**) + orchestrator (227) green (+11: the §1-type filter, `runVectorTuningEmission` dry/live/idempotent/genFailed, the emit-vector-tuning route wiring); a clean production build; and a **live e2e** (`vector-tuning-audit.spec.js`) — the trigger renders and a real dry-run scan surfaces the counts, never generating or posting. *Still deferred (the genuinely-hard part): generation is synchronous on "generate & post" — bounded by the low `--limit`, but streaming the proposals in via SSE as each completes is the next refinement, naturally paired with the scheduler work.*
- **Still open:** Orchestrator v0.2 (v0.1 is **done** — 97 tests; v0.2 = batch cadence, spawn-from-project, scheduled tasks, ~1200–1500 LOC) — the **autonomous scheduler** (auto-fire a cycle without a human click) lives here, the watch-and-steer counterpart to everything above; the rest of the Weave's **posting half** — the harder *generative* proposal types that need real Weave reasoning, not just detection: **vector-tuning is shipped** as the first generative type (CLI + terminal, both done), leaving **mirror sweeps** as the open generative one — plus the remaining executor ops (`stage_transition`, `label_enrichment`) as the Weave starts emitting them (`set-vector` / `add-link` / `set-type` shipped).

**Phase 2 — Authoring: end the bounce.** Mature STATE frontmatter forms (schema un-mistypeable by construction, satisfying SCHEMA §7 through the UI), the body editor with `[[wikilink]]` autocomplete + inline enrichment preview, the bundle-aware navigator, and the concurrent-edit-with-Obsidian conflict surface. Scope honestly: most generative ceremonies stay in chat (show-before-write); this targets quick tweaks + the structured-frontmatter guarantee + review.

**Phase 3 — Sense-making & Lens.** The Topology Lens in STATE (graph fed by `_ops/maps/palace-map-*.json`); [[The Lens]] as a draggable STATE-deck glass (render page A through page B's apparatus); and formalizing [[Palace Enchantment]] as a callable ceremony with a verifiable postcondition — closing the last conceptual gap on the integration list.
