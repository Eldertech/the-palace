# Blender + conditioning pipeline — Gotcha report, 2026-06-13

Session 1 of the [[BLUELINE — Claude Code Job]] (Mac-side, Apple Silicon, MPS, 32 GB unified).
Keystone question: *can a posed 3D scene reliably become clean multi-ControlNet conditioning, and
does "blocked, not prompted" defeat the front-on default?* This report holds what bit, what worked,
and the tool-decision evidence. Verdict block at the end.

## GOTCHA — MPS speed: SDXL + 3 ControlNets thrashes by default

First blocked render ran at **~50 s/it** (28 steps ≈ 23 min for the fill alone). Cause: under MPS
`vram state: SHARED` with ComfyUI's default smart-memory, SDXL (~7 GB) + 3 ControlNets (~7 GB) +
activations at 832×1216 exceeds the comfortable budget, so weights get offloaded/reloaded **between
steps**. Fixes that worked, in order of impact:
1. Restart the server with **`--highvram`** (keep all models resident, no per-step offload) +
   **`--use-split-cross-attention`** (lighter attention) → **50 → 15 s/it**.
2. Drop fill resolution **832×1216 → 768×1024** (still an SDXL bucket).
3. Make the **1.5× refine a plain img2img hires pass (no ControlNet)** — the composition is already
   locked by the fill's ControlNets, so re-applying 3 CN at 1152×1536 only adds cost + OOM risk.

Net: 3-ControlNet SDXL is usable on this Mac but is **not free** — budget ~15 s/it for the fill.
This is the cost the [[Shop/ComfyUI]] resource-scheduling rule should note for multi-ControlNet jobs.

## GOTCHA — SDXL has no strong standalone *lineart* ControlNet (at this date)

The toyxyz recipe and the job both name a **lineart/pose/depth** stack. But xinsir's strong
per-channel SDXL ControlNets are **pose / depth / canny** — there is no strong standalone *SDXL
lineart* ControlNet (lineart lives in the ControlNet-Union model, or in SD1.5 / FLUX). So the honest
per-channel SDXL stack is **pose + depth + canny**, with **canny carrying the edge channel** that
lineart would carry. `lineart.png` is still emitted (XDoG stand-in) as an artifact for completeness,
but is **not fed** to the SDXL stack. → Recommendation: on SDXL, the channel triple is pose/depth/canny;
reserve lineart for the FLUX / SD1.5 path or use ControlNet-Union if a single-model lineart is needed
(which violates the recipe's one-CN-per-channel rule — a real tension, see below).

## GOTCHA — geometric pose projection beats 2D estimation on a proxy

The toyxyz recipe's open question — *toyxyz rig vs a bespoke pass-emission script* — resolves toward
**bespoke geometric projection** for a Blender-native pipeline:
- The OpenPose skeleton is produced by projecting the armature's COCO-18 joints to camera space
  (`bpy_extras.world_to_camera_view`) and drawing the canonical skeleton. It is **exact regardless of
  how abstract the proxy looks**, needs no model download, and is deterministic.
- Running a 2D estimator (**DWPose**) on the clay render is the comparison leg (see Verdict). On an
  abstract greybox proxy, estimators are expected to struggle (they are trained on real humans) —
  which is precisely why the geometric route is the reliable one for "blocked, not prompted."
- The **toyxyz Gumroad rig** was not acquired (needs Loudon's checkout); the bespoke script is its
  functional equivalent for this pipeline and is the recommended default for a scripted, headless,
  reproducible Blender→ControlNet bridge. Acquire the toyxyz rig only if hand-GUI posing of an
  OpenPose-bones armature is preferred over the script.

## Blender pass-emission notes

- All passes emitted from **one camera, one script run, identical resolution** → structural
  registration (no alignment step needed). This is the cleanest property of doing conditioning in
  Blender vs estimating passes from a flat render.
- **Depth** = a material-swap emission shader (`CameraData → MapRange → Emission`), near/far
  **auto-ranged** from joint distances (logged in `pose_keypoints.json`). Cleaner than MiDaS/depth-
  estimation because it is true geometry.
- **Normal** = camera-space normal via `Geometry.Normal → VectorTransform(world→camera) → Emission`.
  Emitted as an artifact (no SDXL normal ControlNet in the downloaded set).
- Body built from **fused metaballs** (a connected clay mannequin) — the first cone-capsule attempt
  read as disconnected parts; metaballs fuse into a legible silhouette and read well in all passes.
- A near-frontal camera **collapses a foreshortened lunge** (legs fuse in projection); a **3/4
  worm's-eye** separates fore/aft limbs and reads the drama. Recorded as a staging gotcha.

## Hand-editability

The `.blend` ships with a poseable armature (`Mannequin_Rig`). The body is generated from the joint
table, so the current re-pose loop is **edit the armature / J table → re-run `pose_and_emit.py` →
fresh passes**. A future enhancement skins the metaball body to the armature so GUI re-posing updates
the mesh live (noted for the recipe; not needed for the spike).

## VERDICT

**Keystone: YES — decisively.** Blocking defeats the front-on default and the drama survives the fill.
See `renders/CONTACT-SHEET-keystone.png`.

- **BLOCKED** (`blocked_sdxl_refined.png`): a worm's-eye over-the-shoulder warrior with the sword
  foreshortened toward the lens, body twisted, in a cinematic canyon — the exact dramatic camera +
  pose authored in Blender. Identity/structure tracks the proxy: the orientation, the extended
  sword-arm, the low angle all carried through.
- **PROMPT-ONLY** (`prompt_only_sdxl_seed7.png`, `_seed42.png`): same prompt, no conditioning →
  both seeds land **centered, eye-level, frontal**. Seed 7 is a dead-static silhouette; seed 42 is
  more dynamic but *still* a centered frontal character shot. The worm's-eye / OTS / foreshortened
  camera that the blocked render nails is something **no prompt-only seed reached**. The "front-on
  default" is a real attractor; geometry is what escapes it.

**OpenPose vs DWPose: use the geometric (projected-bone) skeleton, not an estimator.** DWPose run on
the clay render returned a **fully black image (max-luminance 0)** — zero keypoints detected on the
abstract proxy. The geometric `openpose.png` (projected COCO-18) drove the pose channel correctly.
→ For a Blender-native pipeline, **emit OpenPose geometrically** (toyxyz rig or the bespoke script);
do **not** round-trip through a 2D estimator. (DWPose remains the right tool when the source is a
*photoreal* render or real footage — not a greybox.)

**SDXL vs FLUX (this date): SDXL only, FLUX deferred by decision.** A real FLUX *ControlNet*
comparison needs FLUX installed locally (~40 GB, FLUX.1-dev gated, slow on MPS) and reverses the
`FLUX (Hugging Face)` Specialist's documented cloud-only Lost Branch. SDXL alone proved the entire
keystone here. **Recommendation:** keep SDXL as the conditioning default for now; schedule a focused
FLUX-local follow-up only if SDXL fidelity proves insufficient on a real BLUELINE shot. The FLUX
Specialist stays cloud-text-to-image; "FLUX ControlNet" is a separate, heavier capability to stand
up deliberately, not a drop-in.

**Preprocessor / channel defaults (SDXL):**
- **Pose:** geometric projection → strength **0.9**, full range. The load-bearing channel.
- **Depth:** Blender Z pass (true geometry) → strength **0.7**, full range. Governs front/back ordering.
- **Edge:** **canny** → strength **0.45**, early-only (`end_percent 0.5`) so it guides structure then
  releases for detail. (Canny stands in for lineart — no strong SDXL lineart CN; see gap above.)
- **Refine:** plain img2img hires, **no CN**, denoise **0.42**, 1.5×. Composition is already locked.

**Per-channel vs Union (the `ControlNet Workflow Mastery` tension):** Session 1 ran **one preprocessor
+ one ControlNet per channel** (the toyxyz rule) and it works cleanly. The ghost `ControlNet Workflow
Mastery` entry's premise — a single **ControlNet-Union** model spanning modalities — was **not** tested
here and remains the open comparison. The per-channel route's advantage observed: independent
strength + range scheduling per channel (pose hard, depth medium, canny early-release), which a single
Union model cannot express. → If that ghost entry is ever written, Session 1 is its per-channel arm;
a Union arm is still owed.

## Speed (reference host: mac, MPS, 32 GB unified)

| Step | Cost |
|---|---|
| Blender pose + 3 passes + .blend (Sketch greybox, EEVEE) | ~8 s |
| SDXL fill, 768×1024, 28 steps, **3 ControlNets** | ~15–18 s/it (incl. one-time model + 3×CN load) |
| 1.5× img2img refine, 1152×1536, 15 steps, no CN | folded into the 555 s two-pass total |
| **Blocked two-pass total** | **~555 s (~9 min)** |
| Warm plain SDXL, 768×1024, 28 steps, **no CN** | ~78 s (~2.8 s/it) |
| DWPose estimator on the clay render | ~15 s (empty result) |

The 3-ControlNet fill is the cost driver. Multi-ControlNet SDXL on this Mac is **viable but not cheap**
— plan one fill ≈ a few minutes, not seconds. Optimization (fp8 CN, fewer steps, ControlNet-Union,
or cloud) is the *next* lever, per capability-first: it worked; now it can be made cheaper.

**ComfyUI install layout + MPS session drift.** The checkout is at `_tools/ComfyUI/` directly (not `_tools/ComfyUI/ComfyUI/`); `_tools/` is gitignored. A long-idle server often runs on :8188 — start a second instance on another port with `--database-url "sqlite:////tmp/<name>.db"` to dodge the DB lock. **MPS degrades over a long session:** single-ControlNet SDXL that starts ~3 s/it drifts to 12–37 s/it and eventually blows a 900 s render timeout after a few dozen renders in one server lifetime (memory fragmentation under `vram state: SHARED`, even with system RAM ~50% free). Fix: `kill` the process and relaunch — speed returns to ~3 s/it immediately. Budget a fresh restart between long batch sessions.
