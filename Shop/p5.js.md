# p5.js

![[p5.js — hero.png]]

*First job landed 2026-05-10 (Kuramoto Round 1, Step 2). Status promoted from `stub` to `alive`. Processing (Java) remains named as lineage but is not separately wrapped — most palace interactive work is web-deployable, which makes p5.js the operating tool. If a Java-only sketch becomes essential later, this entry adopts a Processing variant rather than spawning a new Specialist.*

## Charter

I make interactive visual sketches. Generative graphics, simple games, music visualizers, parameter explorers, didactic demos — code that draws and responds. Run in a browser, embed in palace artifacts, export frames for video, or stand alone as a single HTML file. The Maker hands me a sketch concept, a tier, and a deployment context; I deliver a runnable HTML/JS sketch.

I refuse jobs that need production-quality video (Manim, Remotion), serious audio synthesis (Tone.js, RNBO), or real 3D engine work (Three.js). I'm fast and immediate, not deep on any of those.

## Voice

The fast sketcher. Casey Reas / Ben Fry lineage runs through every line. Loves `setup()` and `draw()`, loves seeing a parameter change show up immediately, loves the demo-able prototype. Knows when to reach for `noLoop()` for static work and when to lean into 60fps animation. Comfortable with mouse / keyboard / touch / audio input. Will reach for libraries (`p5.sound`, `p5.gui`, `p5.collide2d`) when the job needs them.

Speaks the language of *sketch* with no apology — these are studies in code that may or may not become Pieces.

## Capabilities

- 2D canvas rendering; WebGL mode for 3D
- Real-time animation via `draw()` loop at 60fps default
- Mouse / keyboard / touch / pointer input
- Audio synthesis and analysis via `p5.sound` (oscillators, envelopes, FFT, mic input)
- Image and video export via canvas-capture or built-in `saveCanvas()` / `saveFrames()`
- Web-deployable: single HTML file with script tags, or embedded in larger pages
- Library ecosystem: `p5.sound`, `p5.dom`, `p5.collide2d`, `p5.gui`, `ml5.js`, and more
- Processing (Java) as a sister runtime when JavaScript performance is insufficient (rare)

## Strengths

- **Speed of authoring:** minutes from idea to running sketch
- **Web-deployability:** outputs run anywhere a browser does, including palace local server and claude.ai artifacts
- Educational ecosystem is vast — code patterns are well-documented
- Audio integration via `p5.sound` is decent for sketches (Tone.js is tighter for serious audio work)
- Live coding is natural; iterating on parameters in real time is the workflow

## Limits

- Performance ceiling is browser canvas; complex 60fps generative work can hit limits
- Fine-grained shader control requires WebGL mode and `createShader()` — workable but not the strength
- Not the right tool for production-quality video (route to Manim or Remotion)
- `p5.sound` is fine for sketches; serious music software work belongs in Tone.js or RNBO
- Single-threaded JS limits parallel computation; web workers help but break the simple model

## Tiers

### Sketch
- Single HTML file or p5 web editor link, no polish, no documentation
- Parameter exploration and concept validation
- Time: 5–30 minutes from concept to running
- Sacrifices: visual polish, error handling, deployment robustness

### Study *(default)*
- Cleaned-up sketch in palace, parameter tuning, palette-aware, deployable on local server
- Time: 1–3 hours including iteration
- Sacrifices: claude.ai artifact polish, documentation completeness

### Piece
- Artifact-ready interactive: palace palette, multiple input modes, mobile-friendly, embed-ready in Loudon Live or claude.ai artifact, accompanied by a recipe entry explaining the concept
- Maker review pass for visual and interaction polish
- Time: half a day or more
- Sacrifices: time

## Job Contract

### Output
- HTML file (and supporting JS/CSS as needed) at `out_path`
- Standards report: `dimensions`, `framerate_target`, `libraries_loaded`, `inputs_supported`, `tier_used`, `gotchas_hit`, `status`, `notes`

## Iteration Character

Deeply iterative; live coding is the natural mode. Refinement happens by:

1. Editing the sketch in real time (browser auto-reloads)
2. Tuning parameters via `p5.gui` or simple HTML controls
3. Adding input modes
4. Re-tiering up

## Self-Check

HTML loads without errors, all libraries resolve, sketch runs at target framerate (within tolerance), declared inputs are wired up.

## Resource Footprint

- CPU: bounded by browser; modest at sketch scale
- RAM: minimal
- GPU: optional (WebGL mode uses it)
- Disk: trivial; sketches are small files
- Network: required only for CDN-loaded p5.js library (or self-host for offline)
- API keys: none

## Gotchas

**2026-05-10 — Background-tab `requestAnimationFrame` throttling.** When the host browser tab is unfocused or off-screen, browsers throttle rAF to ~1 Hz. A Kuramoto-style integrator using `dt = clamp(now - lastTime, 0.05)` will then advance simulation time by only ~0.05 s per second of wall-clock. For verification flows (programmatic browser drivers, screenshots, etc.) this looks like a frozen simulation. The clamp is correct for protecting against initial-frame catastrophe, but the visible behavior is misleading. Mitigations: (a) drive the simulation off a `setInterval`-backed timer rather than rAF when verification is needed; (b) note clearly in the Sketch that focus is required for live behavior. Sketch tier accepts the throttle as a known limit.

**2026-05-10 — Sketches at Sketch tier under-use vertical space.** The first job's canvas (1080×480) put phasors at y=90 and trace baseline at y=320, leaving ~70 px of empty canvas below the trace axis. Cosmetic at Sketch, but flag for Study/Piece tier promotion: re-aspect the canvas or move readouts/labels into the unused band.

**2026-05-29 — Headless harness can PAUSE `requestAnimationFrame` entirely, not just throttle it.** The 2026-05-10 gotcha noted background-tab rAF *throttling* to ~1 Hz. The [[Flocking]] verification (Claude Preview static-server harness) was worse: rAF callbacks never fired at all (a probe counter stayed at 0). p5's whole `draw()` loop is rAF-driven, so the canvas showed only `setup()`'s background and nothing moved. Mitigation that keeps the idiomatic 60 fps loop intact for real browsers: expose the instance with a labeled seam (`window.__flock = p` in `setup()`) so a verification flow can force frames via `__flock.redraw()`. Pumped 450 frames this way and the flock rendered correctly. Lesson: when an interactive p5 sketch must be verified headlessly, give it a redraw seam rather than converting the whole loop to `setInterval` (which would degrade trail smoothness on real tabs). Compare to the sibling [[Observable Plot]] sketch, where `setInterval` *is* the right production choice because it's a slow analytical re-render, not smooth animation.

**2026-05-29 — Fading trails: veil, don't clear.** Confirmed again. A low-alpha full-canvas `rect` each frame (`fill(h,s,b,14)` in HSB) leaves the fading trail; `background()`/`clear()` each frame destroys it. The trail length is framerate-dependent — at 30 fps the veil accumulates differently than at 60 fps, which matters if a sketch is ever moved to a fixed-rate timer.

## Recipes

**2026-05-10 — Two phasors, coupling explorer** (Sketch tier, single HTML file). Two oscillators at 1.00 / 1.07 Hz with K slider (0 → 1.5) and time-speed slider. Order parameter R rendered both as a small in-canvas vector and as a numeric readout. Symmetric Kuramoto integration at `draw()` rate via Euler. Color palette: indigo `#6366F1`, amber `#F59E0B`, dark background `#0B0B10`. Source + deliverable in one file: [Kuramoto Coupling/two-phasors-coupling-explorer.html](../Kuramoto Coupling/two-phasors-coupling-explorer.html). p5.js loaded via CDN (jsDelivr); no build step.

**2026-05-29 — Reynolds boids, expressive interpretation** (Sketch tier, single HTML file; [[Flocking]] shoot-out, second p5 job). The same seed-7 model the D3 and Plot Specimens run, rendered as algorithmic art: fading trails (HSB veil each frame), color-by-velocity (hue = heading angle), oriented darts, no chrome / no controls. The lens makes alignment legible as hue coherence — a coherent flock reads as a colour field before any number is computed. Shared `computeVelocities` block byte-identical to the other two Specimens (Node-proven deterministic). CDN p5@1.10.0. Source + deliverable: [Flocking/flocking-p5-expressive.html](../Flocking/flocking-p5-expressive.html). Standards report: [flocking-p5-expressive.report.json](../Flocking/flocking-p5-expressive.report.json).

## Working within the Loudon Live design system

Canonical sources in `_ops/loudon-live/design-system/`: `colors_and_type.css` + `palace-tokens.js`. p5 is **additive** like D3, with one twist unique to expressive work.

**The update-safe pattern:**
1. Link `colors_and_type.css`, set `<html class="skin-strobe">`, load `palace-tokens.js`.
2. Read `palaceTokens()` in `setup()`: canvas ground / trail veil = `T.bg` (convert hex→rgb for the veil's alpha fill), any marks/chrome-on-canvas = the relevant tokens. HTML chrome uses `var(--token)`.
3. **The deviation rule — the one special to the expressive lens.** An interior may *leave* the palette when colour or space IS the data (colour-by-velocity maps hue to heading — a channel, not decoration). When it does, declare a `deviation_reason` and let the skin keep the ground, chrome, and wordmark. *Skin the frame, declare the interior.*
4. Trails still veil (low-alpha rect), now in `T.bg` so they fade to the skin's own ground rather than a hardcoded near-black. **No hex literals** — the only stale-risk is one you typed.

Exemplar: [flocking-p5-expressive-strobe.html](../Flocking/flocking-p5-expressive-strobe.html) — Strobe chrome (performance register), full-spectrum canvas as a declared deviation. The rAF-pause verification seam (`window.__flock`) is documented in Gotchas.

## Open Questions

- Should sketches be committed as single HTML files or as Vite/esbuild projects with bundled dependencies? Single-file sketches are simpler to share; bundled projects are easier to extend.
- `p5.sound` vs Tone.js for audio-driven sketches — when does the Maker route to which? Likely Tone.js for serious audio work, `p5.sound` for casual visualization.
- Processing (Java) — currently noted as lineage rather than as a wrapped tool. Threshold for adopting Processing as a separate Specialist: TBD; only if a Java-only library or performance need surfaces.

## Lost Branches

- Vanilla canvas API as an alternative — discarded for p5.js's much faster authorship and large educational ecosystem.
