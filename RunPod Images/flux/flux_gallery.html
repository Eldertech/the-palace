FLUX vs SDXL — The Report

Why a second model

SDXL base 1.0 (~3.5B params) is a capable but two-generations-old workhorse: superb at stylized work, unreliable at text and hands. FLUX.1-dev (~12B params, fp8 here) is the current open frontier — a much larger transformer with a T5 language-model text encoder. We pointed a second self-provisioned RunPod endpoint (palace-flux) at runpod/worker-comfyui:5.8.4-flux1-dev-fp8 and re-ran comparable work.

*FLUX per-image cost is higher both because each render takes ~2.5× longer and because this run kept a warm worker (workersMin=1) to stay responsive while you fed prompts — that idle time bills. Scaled to zero like the SDXL run, marginal cost would be lower.

Image-to-image findings

img2img works on the endpoint today (the worker accepts an input image; the workflow encodes it as the sampler's latent start). The 30-frame movie used denoise 0.62 — enough to hold the pose and the legible "business" across every frame, but deliberately conservative, which is why the era/outfit shifts read as subtle rather than dramatic. Pushing denoise higher gives bolder change at the cost of pose drift. The clean way to get both — locked pose AND bold restyling — is a ControlNet (pose/depth) conditioning, which needs the control models added via a network volume. That's the next build-out the backend doc anticipated.

Time & cost

60 FLUX images, zero failures, ~32s average each (~32 min total GPU time). FLUX-phase spend ~$2.33; whole session across both models ~$2.66. Both endpoints now scale to zero — nothing bills at rest.

Bottom line

For anything with text, hands, or precise prompt adherence, FLUX is the clear winner and worth the extra seconds and cents. For fast, high-volume stylized work, SDXL still earns its place. Having both wired into the same RunPod backend means the Maker can route per brief — exactly the cost/quality tier negotiation the Shop is built around.
